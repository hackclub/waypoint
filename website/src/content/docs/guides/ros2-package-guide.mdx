Your ROS 2 package is the last thing required for a Waypoint submission! It is the source code that will run on the Raspberry Pi in your kit.

ROS 2 lets separate programs communicate using named interfaces. It is not a desktop operating system. A **node** is one running program with a focused job, a **topic** is a named stream of messages, and a **message type** defines the fields and units on that topic.

By the time you finish this guide, your repository should contain a package that:

- accepts standard `Twist` movement commands on `/cmd_vel`
- turns those commands into real motor-driver output for your robot hardware
- publishes data from the required IMU on `/imu/data_raw`
- publishes open-loop dead reckoning because Waypoint kits do not include wheel encoders
- works with standard ROS keyboard teleop and includes a small autonomous routine you wrote
- has configuration and launch files that make the package understandable to someone else

Make your own code. The pin assignments, package name, motor settings, IMU orientation, and autonomous behavior should come from your own design.

## What You Are Building

Standard ROS interfaces let teleop, inspection tools, your motor node, and your autonomous node work together without every tool knowing your motor wiring.

| Node | Input | Output | Job |
| --- | --- | --- | --- |
| Motor driver | `/cmd_vel` (`Twist`) | your motor driver's real control signals | move the chassis |
| IMU | physical I2C readings | `/imu/data_raw` (`Imu`) | report acceleration and turn rate |
| Open-loop odometry | `/cmd_vel` | `/odom`, `/path`, and `odom -> base_link` | estimate commanded motion |
| Autonomous routine | its timing or state | `/cmd_vel` (`Twist`) | make the robot follow your short routine |

Teleop and autonomy both publish the same `Twist` message. Do not run them at the same time unless you deliberately add code to cleanly switch between them!

:::tip[Note]
Open-loop odometry is an estimate based on commanded movement. Without wheel encoders, it cannot prove how far the robot physically moved, and drift is expected.
:::

## Three Phases

**Phase A: Learn ROS 2 on the computer**

Install ROS 2 Jazzy, run official examples, inspect nodes and topics, understand workspaces and packages, and create a tiny first node.

**Phase B: Write your package**

Create the package structure, define motor commands, write open-loop odometry, write the IMU publisher, add teleop, add an autonomous routine, and create launch/config files.

## Learn From Real Code

Use examples to answer a specific question, then write the version that fits your robot:

- [ROS 2's official package guide](https://docs.ros.org/en/jazzy/How-To-Guides/Developing-a-ROS-2-Package.html) is the best reference for package structure, `package.xml`, `setup.py`, and Python executables.
- [ROS 2's Python publisher/subscriber tutorial](https://docs.ros.org/en/jazzy/Tutorials/Beginner-Client-Libraries/Writing-A-Simple-Py-Publisher-And-Subscriber.html) is the best starting point for `rclpy` node structure.
- [OrphBot's example package](https://github.com/SharKingStudios/orphbot-package) is the example Waypoint robot package. Inspect one file at a time to answer a specific question, such as where `console_scripts` entries live or which values are OrphBot-specific hardware choices.
- [Terralift](https://github.com/SharKingStudios/Terralift) is a larger real robot. Its drivetrain, IMU, and open-loop odometry nodes show how the same ideas grow in a more complex project. (This is the real robot I used for my research project!)

Do not rename an example package and submit it. Your submission must be your own!
